## 1. What was built

1. **CUDA Utilities & RAII Container** (`src/common/cuda_utils.h`):
   - `CUDA_CHECK` and `CUBLAS_CHECK` error assertion macros.
   - `DeviceBuffer<T>`: RAII buffer managing `cudaMalloc`, `cudaFree`, `copy_from_host`, and `copy_to_host`.
   - `CudaTimer`: RAII event timer wrapping `cudaEventCreate`, `cudaEventRecord`, and `cudaEventElapsedTime`.

2. **CUDA Kernels** (`src/cuda/`):
   - `embedding.cu`: Token embedding lookup (`half* out`, `half* table`, `int64_t* ids`).
   - `rmsnorm.cu`: RMSNorm with FP32 accumulation, warp-level shuffle reduction and shared memory reduction.
   - `rope.cu`: Half-split rotary position embedding matching Qwen2 rotate-half `[-x2, x1]` and base $\theta = 1,000,000$.
   - `causal_attention.cu`: Naive causal GQA kernel (1 block per head $\times$ query token, group size 7, FP32 accumulator for attention logits, online softmax).
   - `softmax.cu`: Standalone numerically stable softmax kernel over last dimension.
   - `swiglu.cu`: Elementwise SwiGLU kernel ($\text{silu}(\text{gate}) \cdot \text{up}$).
   - `residual_add.cu`: Elementwise vector addition in FP16.
   - `bias_add.cu`: 2D broadcast bias addition.
   - `matmul.cu`: PyTorch row-major linear layer evaluation ($C = A B^T$) using cuBLAS `cublasGemmEx` (FP16 input/output, FP32 compute).

3. **GPU Forward Pass & Weights Upload** (`src/model/forward_gpu.h`, `src/model/forward_gpu.cu`):
   - `ModelWeightsGPU`: Safetensors BF16 model parameters converted directly to FP16 on device upload. Tied word embeddings: `lm_head` shares the embedding buffer directly without reallocation.
   - `ActivationBuffersGPU`: Pre-allocated activation memory allocated once at initialization for maximum sequence length (4096). Zero `cudaMalloc` allocations per forward step.
   - `forward_gpu`: Evaluates entire 24-layer transformer architecture on GPU, supports `.npy` dump hooks matching CPU reference, and supports high-resolution per-kernel profiling.

4. **CLI Harness & Observability** (`apps/generate.cpp`, `scripts/bench.py`):
   - Extended `generate.exe` with `--gpu`, `--dump-all-gpu`, `--verify-greedy-gpu`, and `--profile-step`.
   - Updated `scripts/bench.py` with `benchmark_p3_gpu` logging SM clock, memory clock, temperature, and throttle state to `docs/profiles/p3_gpu_p{128,512}_nvml.csv`.

### 4. GPU FP16 Teacher-Forced Gate Verification (`docs/GATES.md`)
Command:
```powershell
python -c "
import os, numpy as np

prompts = ['01_short', '02_medium', '03_long', '04_code', '05_unicode', '06_cjk_emoji', '07_chat_template', '08_whitespace_indent']
all_pass = True
for p in prompts:
    ref_logits = np.load(f'data/reference/{p}/logits.npy')[0]
    gpu_logits = np.load(f'data/dump_gpu/{p}/logits.npy')[0]
    if not np.isfinite(gpu_logits).all():
        all_pass = False
        continue
    ref_top1 = np.argmax(ref_logits, axis=-1)
    gpu_top1 = np.argmax(gpu_logits, axis=-1)
    mismatches = np.where(ref_top1 != gpu_top1)[0]
    if len(mismatches) == 0:
        print(f'{p}: 100% top-1 match ({len(ref_top1)}/{len(ref_top1)} tokens)')
    else:
        print(f'{p}: {len(mismatches)} mismatches out of {len(ref_top1)} tokens:')
        for pos in mismatches:
            sorted_ref = np.sort(ref_logits[pos])
            top1_val = sorted_ref[-1]
            top2_val = sorted_ref[-2]
            margin = top1_val - top2_val
            passes_near_tie = margin < 0.05
            print(f'   pos {pos}: ref_top1={ref_top1[pos]}, gpu_top1={gpu_top1[pos]}, margin={margin:.4f}, near-tie pass={passes_near_tie}')
            if not passes_near_tie: all_pass = False

print('GATE GPU FP16 forward teacher-forced VERDICT:', 'PASS' if all_pass else 'FAIL')
"
```

## 4. Deviations from the plan and why
1. **In-Engine Profiling vs CLI nsys**: As documented in `docs/ENV.md`, `nsys.exe` 2023.4.4 requires elevation due to `ReflexStatsTraceLoggingProvider` on Windows 11 with driver 616.x. As instructed by the user, we implemented in-engine `cudaEvent` timing measuring each individual kernel and launch interval into `docs/profiles/P3_profile.md`, while keeping the elevated nsys command documented in `docs/ENV.md`.
2. **cuBLAS Column-Major Handling**: For row-major linear layer $C = A B^T$, with $A \in [M, K]$ and $B \in [N, K]$, cuBLAS views row-major matrices as column-major transposed. Thus $C^T = B A^T$. We configured `cublasGemmEx` with `CUBLAS_OP_T` on $B$ (dimensions $N \times K$) and `CUBLAS_OP_N` on $A$ (dimensions $K \times M$) with $ldb=K, lda=K, ldc=N$, delivering clean exact row-major results in FP16 with FP32 accumulator.

## 5. Open risks and suspected causes of anything unexplained
- In recompute decode mode without a KV cache, each step performs $O(S^2)$ attention computation over the entire preceding context. At prompt length 512, attention alone takes 89.05 ms per step (75% of GPU busy time).
- Host overhead in P3 profiling: The initial ~276 ms host gap measured during 512-token recompute was confounded. Actual CUDA launch overhead is ~5–20 µs per launch (~2–8 ms total for 411 launches). The remaining gap is caused by synchronous per-kernel event synchronization in the instrument, copying 155 MB of logits (all 512 positions) across PCIe, and CPU argmax over 77.8M elements.
- Independent cross-check & calibration via Nsight Compute (`docs/profiles/P3_ncu.csv`):
  - **Kernel Count Validation**: NCU intercepted 1,644 total kernel launches across the 4 forward steps (3 warmup steps + 1 profiled step), exactly **411 kernel launches per forward step**.
  - **Absolute per-step sum of `gpu__time_duration`**:
    - **Step 1 (unprofiled warmup)**: **122.626 ms**
    - **Step 2 (unprofiled warmup)**: **122.652 ms**
    - **Step 4 (last 411 launches, under in-engine profiler)**: **976.702 ms**
  - **Outcome Determination**: **Outcome 3 (the in-engine timer itself changes the execution)**.
    - During warmup steps (1 and 2), where generate.exe runs forward pass without the in-engine timer, NCU measures total GPU kernel execution time as **122.63 ms**, which closely aligns with the baseline in-engine GPU busy time (118.78 ms).
    - However, during Step 4, when the in-engine `CudaTimer` recorded events around every launch, per-kernel GPU execution duration dilated to **976.70 ms** (an ~8x slowdown in hardware kernel duration), and host wall time expanded to **3872.24 ms**. The serial event synchronization in the instrument serializes execution, blocks kernel pipelining, and severely distorts execution timing.
  - **Per-Kernel Comparison Table (Warmup Baseline vs Step 4 Profiled)**:

The in-engine instrument's per-kernel synchronization alters GPU kernel execution duration by nearly an order of magnitude (Outcome 3), confirming that in Task P4 the instrument must be redesigned without per-kernel synchronizations.
