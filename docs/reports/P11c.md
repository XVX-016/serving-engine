### Per-Layer and Non-Layer Node Breakdown
Each layer contains **11 operations (11 nodes)**, not 10:
1. `rmsnorm_kernel`: Input Layernorm ($1 \times 896$)
2. `gemv_kernel<EpiBias>`: Fused QKV Projection ($896 \to 1152$)

7. `gemv_kernel<EpiResidual>`: Output Projection fused with Residual Add ($896 \to 896$)

10. `swiglu_kernel`: SwiGLU Activation ($1 \times 4864$)
11. `gemv_kernel<EpiResidual>`: Down Projection fused with Residual Add ($4864 \to 896$)

**Non-Layer Operations (3 nodes)**:
1. `embedding_lookup_kernel`: Token Embedding Lookup ($1 \to 896$)
2. `rmsnorm_kernel`: Final Layernorm ($1 \times 896$)
3. `cutlass::Kernel2` / `gemv_int8_f32_kernel`: LM Head Projection ($896 \to 151936$)

### Reconciliation Calculation:
$$\text{Total Fused Nodes} = 24 \text{ layers} \times 11 \text{ nodes/layer} + 3 \text{ non-layer nodes} = 264 + 3 = \mathbf{267\text{ nodes}}.$$

The figure "243 launches" assumed single-kernel attention ($24 \times 10 + 3 = 243$). Because decode attention uses Split-K with a partial accumulation kernel and a reduce kernel ($2$ launches per layer), the true count is exactly **267 nodes**.

### Key Inquiries Answered:
1. **Which kernel has 304 warps and why?**:
   - The **fused Gate/Up projection** (`gate_up`) has $N = 9728$.
   - The GEMV kernel assigns 1 warp per row and 32 warps (1024 threads) per thread block.
   - $\text{Grid Size} = \lceil 9728 / 32 \rceil = \mathbf{304\text{ blocks}}$ ($304 \text{ blocks} \times 1\text{ warp/block} = \mathbf{304\text{ warps}}$). Across 24 SMs, this yields only $\mathbf{12.67\text{ active warps per SM}}$ in flight concurrently.
2. **Proof that stripped variant executes every load**:
   - `gemv_int4_stripped_with_sink` accumulates `load_checksum ^= raw.x ^ raw.y ^ raw.z ^ raw.w` across all 128-bit loads, performs a warp shuffle reduction, and writes to an atomic global memory sink (`atomicAdd(checksum_sink, ...)`). The compiler cannot dead-code eliminate any load transaction.
   - The stripped variant achieved **20.48 $\mu$s** (identical to baseline 20.48 $\mu$s), definitively confirming that the math instructions do not throttle the kernel.

## 6. Targeted Fix: Split-K INT4 GEMV (Adopted as New Default)

### Mechanism
On small shapes ($K=896$), a single warp per row results in very few tiles and low warp residency per SM ($<13\text{ warps/SM}$). We implemented a 2-warp Split-K kernel (`gemv_int4_splitk_kernel`):
- Each row $n \in [0, N-1]$ is divided into 2 independent K-slices ($K/2 = 448$ elements each).
- Two warps execute in parallel in the same thread block, doubling active warps per SM.
- Partial accumulations are combined via `__shared__ float s_partial[32]` before writing to DRAM.

### Results
- **Isolation Shapes**:
  - `qkv`: $20.48 \to \mathbf{16.26\ \mu\text{s}}$ (**+20.6% speedup**)
  - `o_proj`: $19.46 \to \mathbf{14.50\ \mu\text{s}}$ (**+25.5% speedup**)
  - `gate_up`: $94.21 \to \mathbf{80.90\ \mu\text{s}}$ (**+14.1% speedup**)
- **Full Model Graph Step (ctx = 128)**:
  - Baseline INT4 Graph Step: **3.608 ms** ($89.5\text{ GB/s}$, $39.2\%$ of roofline)
  - Split-K INT4 Graph Step: **3.281 ms** ($98.4\text{ GB/s}$, **43.1% of roofline**)
  - **Net Win**: **$+9.06\%$ speedup ($-0.327\text{ ms}$ saved)**.
- **Accuracy**: Bit-exact parity ($\Delta_{\text{max}} = 0.000000\text{e}+00$ on single-token decode).
