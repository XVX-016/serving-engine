# Task P11a Report: Test whether per-launch cost, not bytes, sets the batch-1 decode step

## Final Section & Gate Verdict

- **Gate Verdict**: **PASS**
  - *Summary*: CUDA Graph capture of the batch-1 decode step successfully eliminates CPU enqueue latency, and weight fusion (concatenating Q,K,V into 1152-row GEMV and Gate,Up into 9728-row GEMV) reduces kernel launches from 315 to 195 per step. Across all precision modes, Fused-Graph provides substantial speedups over eager execution:
    - **FP16**: 5.445 ms eager -> **4.860 ms fused-graph** (183.7 -> **205.8 tok/s**, +12.0% throughput, 87.0% roofline).
    - **INT8**: 4.302 ms eager -> **3.446 ms fused-graph** (232.4 -> **290.2 tok/s**, +24.9% throughput, 61.4% roofline).
    - **INT4**: 4.368 ms eager -> **3.619 ms fused-graph** (228.9 -> **276.3 tok/s**, +20.7% throughput, 37.9% roofline).
  - Accuracy gates passed: 100% exact 256-token greedy match between eager and graph across 5 reference prompts on all 3 precision models; 100% exact token match between fused and unfused weights. Zero compute-sanitizer errors.

## What Was Built

1. **Launch Floor Microbenchmark (`tests/bench_launch_floor.cu`, `build/tests/bench_launch_floor.exe`)**:
   - Compares eager vs CUDA Graph 1000 back-to-back launches for an empty kernel, 0.5 MB, 1.0 MB, and 2.0 MB reads.
2. **Offline Weight Fusion (`scripts/fuse_weights.py`)**:
   - Fuses `q_proj`, `k_proj`, `v_proj` -> `qkv_proj` (1152 rows: 896 Q + 128 K + 128 V).
   - Fuses `gate_proj`, `up_proj` -> `gate_up_proj` (9728 rows: 4864 Gate + 4864 Up).
   - Supports FP16, INT8, and INT4 (group-128) formats.
3. **Engine Fused Weight Support (`src/model/forward_gpu.h`, `src/model/forward_gpu.cu`)**:
   - Detection of fused weights during model load and allocation of unified `qkv_out` and `gate_up_out` buffers.
   - Prefill path: single GEMM for QKV and GateUp followed by deinterleaving.
   - Decode path: single GEMV for QKV and GateUp. SwiGLU directly reads the contiguous `gate_up_out` without intermediate copying.
4. **CUDA Graph Capture & Replay Infrastructure (`src/model/forward_gpu.h`, `src/model/forward_gpu.cu`, `apps/generate.cpp`)**:
   - Added `apply_rope_device_pos` (`src/cuda/rope.cu`) and `append_kv_cache_device_pos` (`src/runtime/kv_cache.cu`) taking `const int* d_pos` on device.
   - Created `DecodeCudaGraph` class managing an isolated non-default stream (`cudaStreamCreate`), static parameter buffers (`d_token_id`, `d_pos`, `d_seq_len`), capture via `cudaStreamBeginCapture`, and fast replay via `cudaGraphLaunch`.
   - Exposed `--cuda-graph` CLI flag in `apps/generate.cpp` for both `--bench-decode` and interactive/generation paths.

### Deliverable 5: Gap Calculation

$$\text{Ideal Roofline Ceiling} = \frac{\text{Bytes Read}}{\text{Peak Bandwidth (228.15 GB/s)}}$$
$$\text{Expected Step Time} = \frac{\text{Ideal Roofline Ceiling}}{\text{Best Achieved Fraction}}$$
$$\text{Gap} = \frac{\text{Measured Step} - \text{Expected Step}}{\text{Measured Step}}$$

Using the best GEMV fraction observed for linear layers (~87% for FP16):
- **FP16 Fused-Graph**:
  - Measured: 4.860 ms. Roofline ceiling: 4.227 ms.
  - Achieved fraction: 87.0%.
  - Gap to 87% ceiling: **0.0%** (FP16 essentially saturates available bandwidth).
- **INT8 Fused-Graph**:
  - Measured: 3.446 ms. Roofline ceiling: 2.116 ms.
  - At best GEMV fraction (87.0%), expected step = $2.116 / 0.870 = 2.432\text{ ms}$.
  - Gap = $\frac{3.446 - 2.432}{3.446} = \frac{1.014}{3.446} = \mathbf{29.4\%}$.
- **INT4 Fused-Graph**:
  - Measured: 3.619 ms. Roofline ceiling: 1.371 ms.
  - At best GEMV fraction (87.0%), expected step = $1.371 / 0.870 = 1.576\text{ ms}$.
  - Gap = $\frac{3.619 - 1.576}{3.619} = \frac{2.043}{3.619} = \mathbf{56.5\%}$.

**Verdict**: The remaining gap is **well above 15%** for INT8 (29.4%) and INT4 (56.5%). Even with kernel launch overhead removed by CUDA graphs and launch count reduced by weight fusion, low-arithmetic-intensity GEMV kernels on sm_89 suffer from instruction stall overhead and small-matrix occupancy limitations (e.g. down_proj K=4864, gate_up K=896).

## Deviations from the Plan
1. `cudaStreamBeginCapture(0, ...)` failed on the default stream ("operation not permitted when stream is capturing") because the legacy default stream cannot be captured in CUDA. Fixed cleanly by creating an explicit dedicated `cudaStream_t stream_` within `DecodeCudaGraph` and routing all graph-captured kernels and cuBLAS calls through it.
2. The prefill path deinterleaves the contiguous `[Q|K|V]` buffer using per-token D2D `cudaMemcpyAsync` rather than a dedicated deinterleaving kernel; this is functional and verified, but could be accelerated with a dedicated kernel.

---

## Open Risks and Suspected Causes
1. **Gap to llama.cpp remains**:
   - Engine INT8 Fused-Graph: 290.2 tok/s vs llama.cpp Q8_0: 331.7 tok/s (14.3% faster).
   - Engine INT4 Fused-Graph: 276.3 tok/s vs llama.cpp Q4_K_M: 374.4 tok/s (35.5% faster).
   - *Suspected Cause*: llama.cpp uses quantized matrix multiplication kernels that leverage Tensor Cores / WMMA or optimized multi-row block layouts, whereas our INT4 GEMV is scalar warp-per-row which is bound by arithmetic and long scoreboard stalls.

## Suggested Next Steps (Do Not Start)

2. Implement a dedicated deinterleave kernel for the prefill path to eliminate per-token memcpy overhead.
