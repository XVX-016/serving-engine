### Question 3: State exact bytes per step for FP16, INT8 and INT4 (with MB = 1e6). Explain why P11a achieved bandwidth implies bytes about 2.3% below the handover figures.

#### Exact Byte Calculations ($1\text{ MB} = 10^6\text{ bytes}$)
1. **Weights Read per Step**:
   - **FP16 Model**:
     - Layer Weights (QKV: $24 \times 1152 \times 896 \times 2 = 49{,}545{,}216$ B)
     - QKV Biases: $24 \times 1152 \times 2 = 55{,}296$ B
     - O Projections: $24 \times 896 \times 896 \times 2 = 38{,}535{,}168$ B
     - Gate/Up Projections: $24 \times 9728 \times 896 \times 2 = 418{,}381{,}824$ B
     - Down Projections: $24 \times 896 \times 4864 \times 2 = 209{,}190{,}912$ B
     - LayerNorms ($24 \times 2 \times 896 \times 2 + 896 \times 2 = 87{,}808$ B)
     - LM Head: $151{,}936 \times 896 \times 2 = 272{,}269{,}312$ B
     - Total FP16 Weights Read: **988,065,536 Bytes** (**988.066 MB**)
   - **INT8 Model (INT8 Linear + INT8 Head)**:
     - Linear QKV, O, Gate/Up, Down + Scales + Biases: $358{,}577{,}920$ B
     - LayerNorms: $87{,}808$ B
     - LM Head ($151{,}936 \times 896\text{ int8} + 151{,}936 \times 2\text{ scales} = 136{,}438{,}528$ B)
     - Total INT8 Weights Read: **495,104,256 Bytes** (**495.104 MB**)
   - **INT4 Model (INT4 g128 Linear + INT8 Head)**:
     - Linear QKV, O, Gate/Up, Down + Scales + Biases: $184{,}647{,}424$ B
     - LayerNorms: $87{,}808$ B
     - LM Head (INT8): $136{,}438{,}528$ B
     - Total INT4 Weights Read: **321,173,760 Bytes** (**321.174 MB**)

2. **Embedding Row Read**:
   - In decode, only 1 token row is looked up from embedding:
     - FP16: $896 \times 2 = 1{,}792$ Bytes ($0.00179\text{ MB}$)
     - INT8 / INT4: $896 \times 1 + 2 = 898$ Bytes ($0.00090\text{ MB}$)

3. **KV Cache Read at Ctx 128**:
   - $24\text{ layers} \times 2\text{ (K, V)} \times 2\text{ heads} \times 128\text{ tokens} \times 64\text{ dim} \times 2\text{ bytes} = \mathbf{1{,}572{,}864\text{ Bytes}}$ (**1.573 MB**).

4. **Total Exact Bytes per Decode Step at Ctx 128**:
   - **FP16**: $988{,}065{,}536 + 1{,}792 + 1{,}572{,}864 = \mathbf{989{,}640{,}192\text{ Bytes}}$ (**989.640 MB**, $943.80\text{ MiB}$)
   - **INT8**: $495{,}104{,}256 + 898 + 1{,}572{,}864 = \mathbf{496{,}678{,}018\text{ Bytes}}$ (**496.678 MB**, $473.67\text{ MiB}$)
   - **INT4**: $321{,}173{,}760 + 898 + 1{,}572{,}864 = \mathbf{322{,}747{,}522\text{ Bytes}}$ (**322.748 MB**, $307.79\text{ MiB}$)

#### Why P11a Achieved Bandwidth Implied ~2.3% Fewer Bytes:
In P11a's benchmark script (`scripts/bench_p11a_d4.py`), the formula used was:
```python
ach_bw = (bytes_mb / 1024.0) / (med / 1000.0)
```
Where `bytes_mb` was set to `988.0`, `494.0`, and `320.0`.
Because the script divided `bytes_mb` by `1024.0` instead of `1000.0` (or equivalently treated decimal MB as binary MiB without scaling), the numerator was scaled down by a factor of $\frac{1000}{1024} \approx 0.9766$ (a **2.34% deficit**). This unit conversion mismatch deflated the reported bandwidth and roofline efficiency numbers by exactly $\approx 2.3\%$.

### Question 5: Does each ms/step in the P11a table include logits D2H and host sampling, or forward only?
- **It is FORWARD ONLY (GPU execution only)**.
- In `apps/generate.cpp` (lines 142-175), the benchmark loop for `--bench-decode` encloses 32 decode launches inside `ev_start` and `ev_stop`:
  ```cpp
  CUDA_CHECK(cudaEventRecord(ev_start));
  if (use_cuda_graph) {
      for (int s = 0; s < 32; ++s) {
          decode_graph.launch(next_token, ctx + s, buffers_gpu);
      }
  } else {
      for (int s = 0; s < 32; ++s) {
          engine::decode_step_gpu(next_token, ctx + s, ...);
      }
  }
  CUDA_CHECK(cudaEventRecord(ev_stop));
  CUDA_CHECK(cudaEventSynchronize(ev_stop));
  ```
  No `cudaMemcpy(..., cudaMemcpyDeviceToHost)` and no CPU sampling is executed within the timed `ev_start` to `ev_stop` interval.

### Question 7: Does the C++ tokenizer apply NFC itself? What did the P5 interleaved cuBLAS-vs-custom A/B show, and which kernels does the P5 “3.80 ms” cover?
1. **Tokenizer NFC**: The C++ engine's BPE implementation in `src/tokenizer/bpe.cpp` **does not apply NFC normalization itself**. As documented in `docs/reports/P1.md` and `scripts/tokenizer_sweep.py`, input text passed to the tokenizer must already be in NFC (or Python normalization is applied before calling).
2. **P5 Interleaved cuBLAS-vs-custom A/B**: In Task P5, replacing cuBLAS GEMV with custom fused kernels reduced linear projection time from **5.00 ms down to 3.80 ms** (-24.0%), and dropped the non-attention intercept from **6.97 ms to 5.94 ms**.
3. **Kernels covered by the P5 "3.80 ms"**: It covers exactly the **168 linear projection GEMVs across the 24 transformer layers** ($24 \times 7 = 168$: Q, K, V, O, Gate, Up, Down). It **excludes** the LM head ($151{,}936 \times 896$), which remained on cuBLAS/custom FP32 GEMV at 1.10 ms.

### 2. Diagnosis: The Limiting Resource
- **Limiting Resource**: **Instruction Issue & Scoreboard Dependency Stalls from Small Working-Set Dequant Overhead (Memory Latency Hiding Failure)**.
- **Evidence**:
  1. For small batch-1 decode matrices ($N=9728, K=896$), grid size is only 304 blocks (1 warp per row = 304 warps total).
  2. With only 304 warps across 24 SMs ($\approx 12.6$ warps/SM), there are insufficient active warps to tolerate global memory load latency when each thread executes a heavy sequence of bitwise shifts, unpacks, scale conversions, and FMA calculations.
  3. Total instructions executed balloon from $2.42\text{M}$ (INT8) to $6.58\text{M}$ (INT4), tripling instruction count per weight byte. Because each thread only loads 16 bytes per iteration and spends 16 scalar loop iterations unpacking them, the memory pipeline drains between iterations.

### 3. Falsifying Test: Isolated Macro-Matrix Benchmark
To rigorously test whether INT4 GEMV is fundamentally compute-limited or latency-hiding/grid-size limited on small shapes, we designed a benchmark (`tests/bench_falsifying_test.cu`):
- **Query `cudaDeviceProp::l2CacheSize`**: `33,554,432 bytes` (33.55 MB).
- **Working Set Size**: $N = 70,000, K = 4096 \implies \text{Total Traffic} = \mathbf{147.84\text{ MB}}$ (**4.41$\times$ L2 Cache size**).
- **L2 Cache Flush**: 128 MB buffer flushed via `cudaMemset` before every single timed launch.
- **Rules**: 5 warmup + 20 timed iterations with CUDA events.
- **Hypothesis**: If INT4 GEMV were inherently bottlenecked by ALU/math instructions per byte, stripping the dequant math or speeding up unpacking would show a large speedup. Conversely, if memory bandwidth saturates when the grid provides sufficient warps to hide latency on DRAM-scale matrices, all three kernels will achieve identical DRAM bandwidth ($>200\text{ GB/s}$ and $<256\text{ GB/s}$).

#### Falsifying Test Results:
```

Weight Bytes: 143360000 B (143.36 MB)

On small $K=896$ shapes, the issue is that $K$ is too short (only 28 iterations of 32-element chunks) and warp count is too low to overlap loads and ALU unpack.

## Deliverable 6: P12 Megakernel Gap Analysis & Recommendation

### 1. Gap Definitions
- **(a) Addressable by Megakernel**: $(\text{Graph Step} - \text{NCU Kernel Duration Sum}) / \text{Graph Step}$

- **(b) Kernel Efficiency Gap**: $(\text{NCU Kernel Sum} - \text{Bytes} / 228.15\text{ GB/s}) / \text{NCU Kernel Sum}$
  - Measures what intra-kernel optimizations (unrolling, vectorized loads, tiling) could recover.

### 3. P12 Megakernel Rule Evaluation & Recommendation
- **P12 Decision Criterion**: If Gap (a) is under 15% for **both** FP16 and INT4, recommend stopping P12 with a **NEGATIVE RESULT**.
